# フロントエンドとバックエンドの連携メモ

完成形の画面と操作を検討するモックです。画面用の型は暫定モデルで、Go側とのAPI仕様の合意ではありません。

## 取得と保存の境界

| 窓口 | 現在の実装 | API接続時の役割 |
| --- | --- | --- |
| `services/feed.ts` の `getFeed()` | 固定記事の検索・絞り込み・並び替え | API応答の検証と画面用モデルへの変換 |
| `composables/useFeed.ts` | 読み込み・キャンセル・エラー・選択状態 | 通信中の状態と古い応答の破棄を維持 |
| `services/workspace.ts` | プロフィール、複数リポジトリ、保存、コメント、対応状況のブラウザー内保存 | 認証・ユーザーデータAPIとの通信 |
| `composables/useWorkspace.ts` | 保存境界の状態をVueへ反映 | コンポーネントと永続化処理を分離 |
| `types/feed.ts` / `types/workspace.ts` | 画面が必要とする情報の型 | 合意後に不足・欠損・解析途中の表現を更新 |

`getFeed(query, options)` は `Promise<FeedResult>` を返し、`options.signal` で取得を中止できます。`scenario` と `delayMs` はモックの確認用です。画面コンポーネントへ直接通信を散らしません。

一般フィードは12件です。URLの owner/name から固定プロフィールを選び、リポジトリ向けは6件・5件・4件のいずれかになります。実在確認や依存関係の取得は行いません。再現用URLと保存の挙動は [frontend/README.md](../frontend/README.md) に記載しています。

`total` は表示対象を選んだ後、検索・CVSS重要度フィルターを適用する前の件数です。`matchedTotal` は適用後の件数で、ページングはありません。保存済み一覧は取得した記事からさらに絞ります。本番では、保存済みIDを取得可能な一覧の一部と照合するだけでなく、保存記事を取得するAPIが必要です。

## 2026-09-25時点で確認したバックエンド

`git fetch origin --prune` 後の各ブランチを静的に確認しました。バックエンドの起動、外部NVDへの取得、LLMの呼び出し、フロントエンドからの接続は行っていません。

| 参照先 | コミット | 確認できた内容 |
| --- | --- | --- |
| `origin/main` | `240f494` | `server/router.go` のルート登録。ハンドラー本体、Goモジュール、起動用main関数はこのツリーにない |
| `origin/feature/api` | `4dd671e` | CVE一覧ハンドラーとNVDクライアント。解析系ハンドラーは501を返す |
| `origin/feature/crowler` | `9821746` | `src/nvd/client.go` とそのテスト。APIキーレスのNVD取得ライブラリ |
| `origin/feature/local-llm` | `240f494` | 確認時点ではmainと同じコミット。LLM処理の追加コードはない |

`main` のルーターには、`GET /api/cves`、`POST /api/analyses`、`GET /api/analyses/{analysis_id}`、内部処理用POSTが登録されています。コメント上は解析IDによる進捗・レポート取得を意図していますが、応答形式の定義はありません。[ルート定義](https://github.com/K3NLatte/vulns-news/blob/240f494885e5322a7fafd467cfa4c8c925c5ab96/server/router.go#L10-L22)

`feature/api` の `GET /api/cves?limit=` は、NVDから取得した `id` と `description` の配列を返します。既定10件、上限100件で、リクエスト内でNVDの取得完了を待ちます。解析の作成・進捗取得・内部処理は501です。製品、公開日時、CVSS、出典、RepositoryProfile、LLM分析結果はこの応答に含まれません。[一覧ハンドラー](https://github.com/K3NLatte/vulns-news/blob/4dd671e16ba8964bc5f87b73a7a0d6aa5d499217/server/handlers.go#L17-L47)・[未実装の解析ハンドラー](https://github.com/K3NLatte/vulns-news/blob/4dd671e16ba8964bc5f87b73a7a0d6aa5d499217/server/handlers.go#L50-L66)

NVDクライアントは1リクエスト30秒のタイムアウト、リクエスト間隔6秒、ページサイズ2000です。返却型はCVE IDと説明文だけで、英語の説明を優先します。[型と取得設定](https://github.com/K3NLatte/vulns-news/blob/9821746659b28a15fee320a21ac2fda893730e53/src/nvd/client.go#L13-L51)・[待機と説明文の選択](https://github.com/K3NLatte/vulns-news/blob/9821746659b28a15fee320a21ac2fda893730e53/src/nvd/client.go#L69-L107)

今回共有されたフロー図の「200件ごとの処理」は、NVDのHTTPページサイズとは別に決められる単位です。200件バッチ、EcosystemProfiler、Normalizer、決定的マッチング、LLMScreening、DeepAnalysis、ジョブ保存と途中結果の公開は、確認したブランチにはまだ実装されていません。既存の一覧APIに `limit=200` を渡して代用することもできません。

## 非同期表示の提案（バックエンドとは未合意）

フロー図に沿う場合、リポジトリ取得から詳細分析までを1回の画面読み込みとして待たせず、リポジトリ単位の処理と記事単位の結果を分けて表示します。一般フィードと、それまで取得できた記事は操作できる状態を保ちます。

| 処理・判定 | 画面での扱い |
| --- | --- |
| 受付・待機 | 「処理待ち」。リポジトリURLを再送信させず、同じ処理を追跡する |
| リポジトリ取得／構成の抽出 | 対象リポジトリと現在の段階を表示する |
| 脆弱性の正規化／決定的な照合 | 処理件数・候補件数が取得できれば表示。不一致はリポジトリ向けフィードから除外する |
| LLMの選別中 | 既存の結果を保持し、選別済み件数と残件数が分かる場合だけ表示する |
| `possibly_related`／`unknown` | 「未確定」としてフィードへ出す。影響あり・影響なしのどちらにも断定しない。判定理由と不足情報を示す |
| `unrelated` | リポジトリ向けフィードから除外する。一般フィードからも記事を消す、という意味にはしない |
| `related` → DeepAnalysis実行中 | 「詳細分析中」。判明済みのCVE情報を先に見せ、未生成の対策・PoCを作成済みに見せない |
| DeepAnalysis完了 | 「分析済み」。関連性の根拠、対策、PoC、分析時刻を表示する。分析完了は内容の正しさを保証する意味ではない |
| 一部の処理が失敗 | 完了済み記事・未確定記事を残し、失敗した段階または記事だけを再試行できるようにする |

`unknown` は「判定に必要な情報が足りない」という結果で、通信障害やLLM実行失敗とは別です。フロー図では `possibly_related` と `unknown` は未確定フィードへ進むため、画面側の都合で自動的にDeepAnalysisへ流さないようにします。再判定の条件は合意が必要です。

処理段階と、利用者が付ける「未確認・調査中・対応済み・影響なし」は別の状態です。AIの判定が変わっても、利用者の対応状況を勝手に上書きしません。

### 先に合意したい最小限の情報

- **処理の識別**：解析ID、リポジトリID、対象refと解決済みcommit、開始・更新時刻。リポジトリを切り替えても別の処理結果を混ぜないために使います。
- **処理の状態**：待機／実行中／完了／失敗、現在の段階。総数が未確定の場合は未確定として返し、根拠のない進捗率や残り秒数を作りません。
- **途中結果**：安定した記事ID、選別結果、詳細分析の状態、利用可能な項目、不足情報、更新番号またはカーソル。未確定から分析済みへ変わった記事を重複追加せず更新します。
- **件数**：取得、正規化、候補、除外、選別済み、詳細分析済みを分けます。候補が減る工程で、異なる母数の件数を1つの進捗率に混ぜません。
- **失敗と再試行**：失敗した段階・記事、再試行可能か、再試行の対象、重複実行を防ぐ識別方法。同じリポジトリを再読込するたびに新しいLLM処理を始めないために必要です。

ここでは新しいエンドポイントやJSONフィールド名を確定しません。既存の解析作成・解析取得ルートは利用候補ですが、リポジトリ単位の処理にどう対応させるか、途中結果をどこから返すかはGo担当と決めます。

### 再表示・再試行と待ち時間

解析IDを対象リポジトリと結び付け、再読込時はまず既存の処理を取得します。画面の再表示だけで解析作成を再送信しません。最初は解析取得の定期確認でも実装できますが、更新間隔、バックオフ、SSEを使うかはバックエンドと合わせます。非表示タブでは確認頻度を下げます。

リポジトリ切替や画面離脱時は古い取得応答を破棄します。ブラウザーの `AbortSignal` で通信を止めても、サーバーの解析処理が停止したとは扱いません。処理のキャンセル機能を設けるなら、別途その動作を合意します。

再試行中も既存の成功結果を保持し、「いつの処理の結果か」を示します。全体が失敗した場合も一般フィードや別リポジトリへ移動できるようにし、画面全体を長時間のスピナーで塞がない方針です。

## API接続前に合意すること

| 項目 | 決める内容 |
| --- | --- |
| 日付 | 公開・更新・収集日時の区別、タイムゾーン、欠損 |
| CVSS | バージョン、ベクター、スコアの出典、未評価の表示 |
| 悪用とPoC | 悪用確認・PoC公開・未確認の根拠、静的コードの形式 |
| LLM分析 | 出典の事実と推論の区別、根拠、生成日時、未確認事項 |
| リポジトリ | 実在・公開状態、解析開始・進捗・失敗・再解析、直接／間接依存と対象バージョン |
| 関連度と対応優先度 | 算出方法、理由、未評価、到達可能性などをどこまで判断できるか |
| フィード | 検索・並び替えを実行する側、ページング、同順位、件数の意味 |
| ユーザーデータ | 認証方式、権限確認、期限切れ、ゲスト状態の移行、複数リポジトリと保存記事の取得 |
| コメント | 非ログイン投稿を共有するか、保存期間、投稿・削除権限、制限と管理方法 |
| エラー | 入力不備、解析中、権限不足、レート制限、取得失敗と再試行 |

現在の `relevance.score` は0〜100で、関連度順は大きい順、同点は公開が新しい順、記事ID順です。未評価は末尾に置きます。`relevance.priority` は最優先・高・中・低・要確認の別値です。CVSS、依存関係の一致、実際に攻撃が成立する条件を同一視しません。

## 認証・保存・コメント

表示名によるログインはブラウザー内のプロフィール選択です。本人確認やサーバー側の認可はありません。ゲストはsessionStorage、プロフィールはlocalStorageに保持します。これを本番の認証として流用しないでください。

新しいプロフィールへの初回ログインではゲスト状態を移し、保存成功後にゲスト側を空にします。既存プロフィールの場合はゲスト状態を別に残します。コメントはほかの利用者へ送信されません。「非ログインでもコメント可能」と「ほかの人に共有する投稿」は別に設計する必要があります。共有するにはサーバー側の保存が必要です。

## 切り替え時の確認

1. Go担当とレスポンス・エラーの例を合意します。不足項目を架空値で補って実データに見せないようにします。
2. サービス層にAPI通信と実行時のJSON検証を実装します。TypeScriptの型注釈だけでは外部データを検証できません。
3. AbortSignal、読み込み・空結果・エラー・再試行を維持します。
4. モックのプロフィール選択・架空スコア・ローカル認証・scenario指定を本番の取得経路から外します。
5. 合意した応答を使って変換、期限切れ、権限不足、解析中、ページングをテストします。

## セキュリティ上の境界

URLの形式検証はブラウザーで行っていますが、サーバーでもホスト・スキーム・名前解決後の接続先・リダイレクトを検証する必要があります。ブラウザーの検証だけではSSRFや非公開リポジトリへのアクセスを防げません。操作対象の権限もサーバーで確認します。

記事・コメント・LLM出力は文字列として描画し、生HTMLを挿入しません。外部リンクは許可したスキームだけを使います。PoCはexample.invalid宛ての静的テキストで、実行機能はありません。秘密情報をフロントエンドの環境変数やlocalStorageへ持ち込まないでください。

## 個別解析・期限付き追跡の追加案（チーム未合意）

「脆弱性情報版VirusTotal」という利用者の構想を、フロントエンドで操作できる形にした案です。チームの要件合意や、バックエンドへの実装依頼を意味しません。バックエンドは変更しておらず、上記の確認時点で実装されていたのはCVE一覧の取得です。

個別入力、既存レポートの再利用、期限付きの定期更新、期限切れ後の手動再解析、過去情報を含むリポジトリ検索を扱います。モックの操作方法と再現範囲は [frontend/README.md](../frontend/README.md#個別解析共有追跡の追加案チーム未合意) に記載しています。

API接続時には、次の情報を分けて合意する必要があります。エンドポイントやフィールド名は未確定です。

| 対象 | 合意したい内容 |
| --- | --- |
| 入力と重複 | CVE・GHSA・アドバイザリURLの正規化と別名の対応。連打や再送では同じ依頼を再利用する冪等性。URLが同じという理由だけで古い分析を最新と扱わない |
| 解析ジョブ | ジョブID、受付・実行中・完了・失敗・取消、対象、試行回数、利用可能な途中結果。ジョブの完了と脆弱性の影響判定を分ける |
| レポート | ジョブとは独立した安定ID、版、分析日時、出典と確認日時、未確認事項。再解析中も直前の版を閲覧可能にする |
| 追跡 | 期限、次回確認日時、最終確認結果、更新頻度。期限切れ後は明示的な依頼でのみ再解析し、定期追跡の再開は別の操作にする |
| 新着フィード | 新規公開と既存版の更新を区別する。数件から数百件の追加に対応するカーソル・件数・安定した並び順。閲覧中の一覧は通知後、利用者の操作で反映する |
| リポジトリ検索 | 対象commit、調べた情報源と期間、依存関係、照合結果、再利用／新規解析の内訳、ページング用カーソル、未処理範囲と部分失敗。過去情報を含めても「全脆弱性を網羅した」と断定しない |
| 共有 | 公開できるレポートの範囲、固定版／最新版のURL、閲覧権限。個人のリポジトリ情報や入力URLの機密パラメーターを共有URLへ含めない |

追跡7日・確認間隔1日という現在の値は画面確認用の仮定です。利用者ごとに同じCVEを重複解析するか、共通レポートとリポジトリ固有の影響評価を分けるか、更新がない確認も新しい版に数えるかは要相談です。既存結果の鮮度と照合範囲を示すことで、再利用してよいか判断できるようにします。

追加分の `types/reports.ts` と `services/reports.ts` は、入力の形式検証と更新期限の純粋関数です。`useReportLibrary.ts` はローカルの待機演出とセッション保存を担当しています。実APIへの移行時は、画面が作る時刻・進捗・履歴をサーバーの応答へ置き換えます。任意入力から事実・CVSS・対策を推測して補完しません。
