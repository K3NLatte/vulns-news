# フロントエンドとバックエンドの連携メモ

現在は公開フィードの操作を確認するローカルモックです。ここにある型は画面を作るための暫定モデルであり、Go側とのAPI仕様の合意ではありません。エンドポイントや認証方式はまだ決めていません。

## 現在の境界

```text
画面コンポーネント
  → frontend/src/composables/useFeed.ts
  → frontend/src/services/feed.ts の getFeed()
  → frontend/src/mocks/feed.ts
```

| ファイル・関数 | 役割 |
| --- | --- |
| `frontend/src/types/feed.ts` | `FeedQuery`、`FeedItem`、`FeedResult`など、画面が扱う型 |
| `frontend/src/services/feed.ts` の `getFeed()` | 非同期の取得境界。今は固定データの検索・絞り込み・並び替えを実行 |
| 同ファイルの `parseRepositoryUrl()` | HTTPSのGitHubリポジトリURLの形式確認と正規化 |
| `frontend/src/mocks/feed.ts` | 架空の記事12件と分析・依存関係のサンプル |
| `frontend/src/services/feed.test.ts` | 取得境界の振る舞いのテスト |

`getFeed(query, options)` は `Promise<FeedResult>` を返します。`options.signal` で古い読み込みを中止できます。`scenario` と `delayMs` はモックの状態確認用です。

現在の `total` は一般／リポジトリ向けの対象を選んだ後、検索・重要度フィルターをかける前の件数です。`matchedTotal` は両フィルターを適用した後の件数です。ページングはありません。

一般フィードは12件、リポジトリ向けは関連情報付きの6件です。入力URLに応じた解析はせず、全URLで同じサンプルを返します。URLの形式が正しくても、そのリポジトリが存在することや公開されていることを意味しません。

リポジトリ向け表示では `sort: 'relevance'` を指定できます。暫定モデルの `relevance.score` は0〜100のサンプル値で、大きい順に並べます。同点は公開が新しい順、次に記事ID順です。スコアがない記事は末尾に置きます。重要度や直接／間接依存の分類とは別の値として扱います。実際の関連度の算出方法、範囲、未評価の扱いはAPI接続前にGo担当と決めます。

## Go側と合意すること

- **日付**：公開日・更新日・収集日時の区別、タイムゾーン、欠損時の扱い。画面は現在、タイムゾーンを含む日時文字列を受け取ります。
- **重要度とCVSS**：重要度の分類、未評価の表現、CVSSのバージョンとベクター、スコアの出典。現モデルはスコアのみなので拡張が必要です。
- **悪用状況**：悪用確認、PoC公開、未確認の定義と根拠。「未確認」を「悪用されていない」と表示しないようにします。
- **LLMの分析**：出典の事実と生成された推論の区別、根拠、生成日時、モデル情報、信頼度の意味。確認できていない推論を断定表示しないための情報が必要です。
- **リポジトリへの影響**：直接／間接依存、対象バージョン、照合根拠、解析状態。依存関係の一致と、実際に攻撃が到達することは分けます。
- **検索・並び替え・ページング**：処理する側、並び順の同順位ルール、カーソルなどの方式、件数の意味、更新中に記事が増えたときの扱い。
- **認証と保存**：認証方式、期限切れ・権限不足の応答、複数リポジトリ、記事保存、非ログイン時の一時状態とログイン後の永続状態の移行。
- **コメント**：公開投稿と自分だけの一時メモを区別し、非ログインで許可する操作を決めます。他の利用者に共有するコメントには、ログインの有無とは別にサーバー側の保持が必要です。
- **エラー**：入力不備、取得失敗、解析中、レート制限などを画面が区別できる応答と、再試行の条件。

## APIへ切り替える手順

1. 画面で必要な情報をGo担当と確認し、レスポンスとエラーの例を合意します。
2. `services/feed.ts` をAPIレスポンスから画面用モデルへ変換する窓口にします。画面コンポーネントへ直接 `fetch` を散らしません。
3. 外部から来たJSONを実行時に検証します。TypeScriptの型注釈や型アサーションだけでは、レスポンスの構造・値を検証できません。
4. `AbortSignal` を実際の通信にも渡し、古い検索結果で新しい表示を上書きしない動作を維持します。
5. モックのデータと状態切り替えを本番の取得処理から切り離します。現在の `scenario` をAPIの仕様にそのまま持ち込みません。
6. 合意した応答のサンプルで、型変換・空結果・エラー・認証期限切れなどを確認します。検索やページングをサーバー側へ移す場合は、現在のテストも新しい契約へ更新します。

## 実装時の安全性

ブラウザーのURL検証だけでは、サーバーの取得先を安全に制限できません。Go側でも対応するホスト・スキームを検証し、名前解決後の接続先やリダイレクトを含めてSSRFを防ぐ必要があります。認証済みの操作でも、対象リポジトリや保存データへの権限をサーバー側で確認します。

APIキー、LLMへの秘密情報、サーバー用の認証情報をブラウザーへ渡しません。フロントエンドの環境変数も配布物に含まれ得るため、秘密情報の保存先にはできません。

記事・コメント・LLM出力は信頼できない入力として扱い、生HTMLを直接描画しません。現在は文字列として表示します。将来Markdownや外部リンクを扱う場合も、HTMLのサニタイズとURLスキームの検証を別途実装します。PoCの表示が必要になっても、ブラウザーで自動実行しない構成にします。
