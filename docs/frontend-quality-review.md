このコードは、完成形を検討する画面と、本実装へ引き継ぐフロントエンドの土台です。未合意の機能は [PRODUCT.md](../PRODUCT.md)、採用した表示・操作の基準は [DESIGN.md](../DESIGN.md)、実APIとの差は [連携メモ](frontend-integration.md) に分けています。初回の191テスト時点の記録は [frontend-security-review.md](frontend-security-review.md) に残しています。

今回のレビューは、入力と保存・非同期処理・画面操作を分担した確認、別担当による差分の再確認、修正後のブラウザー試験という3段階で進めました。各段階で見つかった不具合を修正し、再現条件をテストへ追加しています。同じ検査を繰り返すだけでなく、別セッション・複数タブ・長文・保存失敗まで操作を組み合わせました。

## レビュー観点

入力は型だけでなく、形式・値の範囲・状態の整合性を境界で確認します。画面から送られる値とブラウザーの保存データも信頼しません。検査の考え方は [OWASP Input Validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html) を参照しています。

| 観点 | このアプリで確認すること | 主な確認箇所・方法 |
| --- | --- | --- |
| 要件と責務 | 一般フィードとリポジトリ向けの区別、CVSSと対応優先度の区別、未評価を確定情報にしない | `PRODUCT.md`、画面用の型、一般・関連・未確定の記事表示 |
| 入力境界 | URLの正規化、許可する形式、長さ、Unicode、CVE・GHSA、重複、空入力、最大件数 | `feed.test.ts`、`reports.test.ts`、`publicUrl.test.ts`、不正入力後に正常操作できるE2E |
| 取得データ | 型違い、欠落、無効な日時、範囲外スコア、重複ID、件数矛盾を画面へ渡さない | `feedContract.test.ts`。TypeScriptの型注釈とは別に実行時検証 |
| 非同期処理 | 応答の順序が逆転しても新しい結果を保持、離脱時の中止、古い失敗で新しい結果を消さない | `useFeed.test.ts`。遅延した成功・失敗を明示的に解決して確認 |
| 解析の状態 | 新規・重複・上限・中止・再試行・再読み込み、期限切れと手動更新、未完了情報の扱い | `useReportLibrary.test.ts`、`reports.test.ts`、解析操作のE2E |
| 保存の整合性 | ゲスト移行、プロフィール隔離、読込・書込失敗、旧データ、別セッション、複数タブ | `workspace.test.ts`、保存拒否・新しいブラウザーコンテキスト・別タブのE2E |
| 描画と外部リンク | HTML風の文字列を実行しない、出典URLを検証、PoCは静的テキストとして扱う | Vueテンプレートの静的確認、コメントの文字列描画と復元、URLテスト |
| 遷移と共有 | 不正なハッシュ、深いリンク、リポジトリ文脈、戻る操作、共有API・クリップボード失敗 | `useNavigation.test.ts`、記事から一覧への復帰、手動コピーへの切替E2E |
| キーボード | 入力エラーの移動先、削除後のフォーカス、ダイアログの終了・復帰、同名ボタンの識別 | コメント・登録・検索・解析・共有ダイアログの操作確認 |
| アクセシビリティ | 見出し、ラベル、状態通知、色の意味、フォーカス、拡大時の読みやすさ | 主要6画面とログインダイアログのaxe検査、キーボード、200%文字サイズ |
| レイアウトの境界 | 左一覧の位置、右記事の本文への到達、狭幅・低い画面・長いID、横はみ出し | `useFeedPanes`、1440px基準の2ブラウザー、モバイル幅・短い画面・長文のE2E |
| 保守性と再現性 | UIと処理の分離、モックの交換箇所、処理破棄後のタイマー・監視解除、固定依存関係 | composables/servicesの差分、型チェック、ビルド、lockfile、テスト実行手順 |

Vueの文字列描画を維持し、利用者やLLM由来の内容をテンプレート・生HTMLへ変換しない方針です。URLは文字列のエスケープだけで安全と判断せず、リンク先の検査も別に行います。[Vue Security](https://vuejs.org/guide/best-practices/security.html)

アクセシビリティの観点は [WCAG 2.2 Quick Reference](https://www.w3.org/WAI/WCAG22/quickref/) を参照しました。自動検査の対象にはWCAG 2.0 A/AA、2.1 AA、2.2 AAのaxeタグを使用しています。自動検査の成功は、WCAG全項目への適合や支援技術での使いやすさの確認を意味しません。[Playwright Accessibility testing](https://playwright.dev/docs/accessibility-testing)

## 今回追加で修正した問題

| 再現した問題 | 修正・回帰確認 |
| --- | --- |
| 古いプロフィールのタブから保存すると、別タブで保存した内容を上書きする | 読込時の保存内容と書込直前の内容を比較。競合時は既存保存を維持し、画面内の変更が未保存であることを通知。キャッシュ済みプロフィールへの再ログインも確認 |
| 追加したCVE等を保存しても、新しいセッションでは元のレポートがなくなり、保存済み一覧から消える | 正規化した入力と作成日時だけをプロフィールへ保持し、検証して記事を再構成。プロフィール隔離、ゲスト移行、保存解除・再保存、別名URLを確認 |
| 定期追加記事の公開日時が、再読み込みのたびに現在時刻へ変わる | 公開日時を保存・復元。別日の再読み込みでも新しい記事にならないことを確認 |
| 画面用データの型を満たさない応答を取得境界で止められない | `parseFeedResult()` を追加し、取得後の画面モデルを検証。Goの生のCVE配列へ架空のスコアや日時を補わず拒否 |
| 共有リンクの文脈に不正なリポジトリURLや壊れたIDが入る | 遷移の読込・生成でIDとURLを検証。不正な文脈を後続の取得へ渡さず、例外にもならないよう確認 |
| 検索クリア・コメント削除・解析中止などで操作したボタンが消え、キーボードの位置を失う | 次の入力欄または対象の見出しへフォーカスを移動。登録エラー・削除確認・Escapeも確認 |
| 記事ページの見出し、複数の中止・再試行ボタン、更新通知が識別しにくい | ページのh1、対象IDを含む操作名、状態通知を追加。日時は年と日本時間を表示 |
| 長い記事ID・見出しが右ペインを占有し、本文の下まで到達できない | 固定部分が大きい場合は右ペイン全体をスクロール可能に変更。長い受理済みIDから保存一覧を開くE2Eで本文末尾への到達を確認 |
| 解析一覧から記事を開いて戻ると、位置・選択タブ・フォーカスを失う | 解析一覧への復帰を取得状態から分離し、選択状態を親で保持。画面内の戻るボタンとブラウザーの戻るを両ブラウザーで確認 |
| コピー操作の連打や失敗時に状態が分かりにくい | 実行中の再操作を抑止。失敗時の手動コピー、Escape、元の操作へのフォーカス復帰を確認 |

保存する追加レポートの参照に本文・CVSS・解析履歴は含めません。別セッションでは未評価として再構成し、前の画面で表示した状態だけを根拠に「分析済み」にしません。ローカルプロフィールの競合検知は、複数タブ間の原子的なロックやサーバー側の同時更新制御を実装したものではありません。

## 試験の再実行

WSLのUbuntuで、リポジトリのルートから実行します。Windows側とWSL側の`node_modules`を混在させないでください。

```bash
nix develop .#
cd frontend
pnpm install --frozen-lockfile
pnpm test
pnpm typecheck
pnpm build
pnpm audit --json
```

ブラウザー試験を初めて実行する環境では、Playwrightのブラウザーを用意します。Linuxのライブラリー不足が案内された場合は、その環境で`pnpm exec playwright install-deps chromium firefox`も実行します。

```bash
pnpm exec playwright install chromium firefox
pnpm test:e2e --repeat-each=2
pnpm exec playwright show-report
```

通常はテスト設定が開発サーバーを`127.0.0.1:4173`で起動します。既に起動した別のサーバーを使う場合だけ、`PLAYWRIGHT_BASE_URL`で明示します。設定は`frontend/playwright.config.ts`、シナリオは`frontend/e2e/`の3ファイルです。ChromiumとFirefoxの各シナリオを2回ずつ実行し、自動リトライはしません。失敗時はスクリーンショットとtraceを残します。

E2Eは見えている操作名・ラベルを中心に対象を選び、状態が成立するまで待つ形にしています。各シナリオは未処理の`pageerror`がないことも確認します。この方針は [Playwright Best Practices](https://playwright.dev/docs/best-practices) に沿っています。

## 未検証・接続時に確認すること

| 境界 | 現状と次の検証 |
| --- | --- |
| Go API | 現在は固定データとローカル取得処理。実サーバーを起動しての接続、NVD取得、LLM実行は未検証。応答変換・欠損・ページング・HTTPエラーを契約後に追加する |
| 認証・認可 | 表示名の切替はブラウザー内のプロフィール選択。本人確認、他人のコメント変更防止、所有権検証をサーバーで実装する。localStorageの値は認証・権限の根拠にしない |
| URL取得とSSRF | ブラウザーでは構文を検査。実取得側でDNS解決後のIP、内部ネットワーク、リダイレクト、接続制限を検証する。公開ドメイン形式だけでは到達先の安全性を保証しない |
| オリジンとセッション | デプロイ先・API接続先・CORS・Cookieまたはトークン・CSRF・セキュリティヘッダーは未確定。許可オリジンやCookie属性を実際の構成で確認する |
| 解析処理 | ローカルの6秒処理、追跡期間・間隔は画面確認用。サーバーのジョブ永続化・再送の重複防止・停止・再接続・レート制限は別途検証する |
| 実データの性能 | 固定記事による操作確認。大量記事、実ネットワーク、長時間のジョブ、多数ユーザーの負荷や性能測定は未実施 |
| 実機と支援技術 | iOS Safari実機、VoiceOver、NVDAによる手動確認は未実施。画面幅のエミュレーションとaxeだけで代替しない |

未合意のCVE追加入力、定期再分析、過去の脆弱性探索などを採用するかはチームで決めます。削除する場合も、検証・保存・画面の責務を分けた構造は維持します。
