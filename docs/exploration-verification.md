# Repository 探索の共通化に関する検証

## 結論

2026年9月25日、従来の `Profile` と実験用の `ProfileWithTraversal` を比較した。検証対象では、ファイル一覧だけでなく `RepositoryProfile` 全体が一致した。固定の脆弱性情報・Screening結果を使った後続の決定的な処理でも一致した。

ただし、すべてのRepositoryやファイルシステムに対する同値性の証明ではない。実際のNVD・OSV・LLMを使った応答の一致は検証対象外である。

同値性の確認後、既定の `Profile` を共有方式へ切り替えた。`cmd/mvp-run` も通常の呼び出しでこの方式を使う。キャッシュは `Profile` の呼び出しごとに新規作成し、別の解析へ持ち越さない。LLMをテンプレートへ置き換える変更は含まない。

比較テストと性能計測では、`ProfileWithTraversal(..., nil)` を従来方式として保持する。差分テストは共有方式同士を比較するのではなく、この従来方式と既定の `Profile` を比較する。呼び出し間でディレクトリを追加・削除しても結果に反映されることもテストする。

## 変更した仕組み

`src/traversal/cache.go` で、ディレクトリの列挙結果を解析処理間で共有する。各処理の除外ディレクトリ、順序、件数・深さ・サイズ制限、安全性の確認は維持する。

各処理がキャッシュ上のエントリを再走査するため、「すべての処理を一つの再帰探索へ統合した」わけではない。また、分割読み取りや上限到達時の代替処理があるため、あらゆるディレクトリでOSへの読み取りが必ず一回になるという保証もない。

ファイル内容の読み取り・解析結果はキャッシュしない。同じファイルの内容を複数の処理で読むコストは残る。

## 比較した結果と条件

`src/repository/profile_traversal_test.go` などで、同じRepository、同じ識別情報、同じ解析時刻を渡して `reflect.DeepEqual` で比較する。要素の順序や `nil` と空スライスの違いも比較対象である。

対象は以下のとおり。

- `RepositoryProfile` 全体：依存情報、バージョン、言語、ソースの観測情報、警告など。
- このプロジェクト自身の実ファイル。
- 多言語・複数形式の既存テスト用Repository。
- npmの入れ子、workspace、近傍のlockfile選択、直接依存と用途の判定。
- 除外ディレクトリの違い、シンボリックリンク、未対応形式の警告。
- 不正なJSON・TOML・YAML・XML、空・不正なルート。
- ソース解析の深さ、ファイルサイズ、ファイル数、エントリ数の上限。
- 固定の架空CVEと固定のScreening結果による `matcher` → `evidence` → `assessment` → `feed.Build` の結果。

最後の比較は決定的な処理の差分検証であり、実LLMによるDeep Analysisの再現性や、脆弱性判定の正しさを証明するものではない。既存解析が未対応の言語や形式への対応が増える変更でもない。

### エラーの差異

存在しないルートでは、従来方式の `stat` とキャッシュ方式の `open` の違いによってエラー文字列が異なる場合がある。このケースでは `*os.PathError`、対象パス、`os.ErrNotExist` が一致することを確認する。他の比較用ケースはエラー文字列も比較する。したがって、全エラー文字列まで無条件に完全互換とはしていない。

## Profile全体の計測

環境はWSL/Linux、amd64、AMD Ryzen 7 7730U、Go 1.27.1。各条件を `-benchtime=500ms -count=3` で計測した。

比較用Repositoryは、100ファイルごとのディレクトリに配置した `.txt` ファイルと、最小の有効な `package.json` で構成する。新方式は毎回 `traversal.New()` から開始するため、前回のProfileのキャッシュを持ち越さない。OSのファイルキャッシュを消す計測ではない。

| 比較用ファイル数 | 従来のProfile | 共有方式のProfile | 中央値の速度比 | 従来の割り当て量 | 共有方式の割り当て量 |
|---|---:|---:|---:|---:|---:|
| 1,000 | 72.1〜72.8 ms | 31.7〜38.3 ms | 約2.1倍 | 約4.19 MB/回 | 約1.55 MB/回 |
| 5,000 | 332.8〜344.6 ms | 168.3〜192.4 ms | 約1.8倍 | 約20.83 MB/回 | 約7.65 MB/回 |

中央値はそれぞれ、従来72.31 msに対して共有34.18 ms、従来338.24 msに対して共有187.69 msだった。割り当て回数は、1,000ファイルで約63,620回から約30,071回、5,000ファイルで約316,820回から約149,089回へ減った。

割り当て量は `B/op` による累計で、最大常駐メモリやピークヒープではない。列挙結果を保持するキャッシュがあるため、割り当て総量が減ってもピークメモリまで減るとは断定できない。

以前の「約10〜12倍」は単純な列挙処理だけの比較だった。今回の実際のProfile全体の測定値と置き換えて説明する必要がある。依存ファイルやソースコードの解析が支配的なRepositoryでは、今回より効果が小さくなる可能性がある。clone・NVD取得・OSV照合・LLM推論を含む処理全体の速度は計測していない。

## 機能面の利点と制約

- 利点：個々の解析規則を変えず、ディレクトリ列挙の重複と再割り当てを減らせる。
- 維持するもの：言語・依存の対応範囲、各処理の除外規則と解析上限、決定的な後続処理への入力。
- 制約：キャッシュは逐次利用専用。同じキャッシュを並列処理から共有してはいけない。
- 制約：解析中に変更されないcheckoutでのみ使う。同じディレクトリ内の変更まで完全に検出する仕組みではない。
- 制約：上限を超える場合は従来の読み取りへ戻る。切り捨てによる高速化はしない。
- 未検証：Windowsでの直接実行、特殊なファイルシステムやI/O障害、大量の実Repository群、ピークメモリ。

現時点では「検証範囲で解析結果を維持し、Profile全体を高速化できた」と判断する。共有方式は既定で有効にしたが、運用対象を広げる際には、対象となる実Repository群と実行環境でも同じ差分テストを行うのが望ましい。

## 再実行用コマンド

以下はGoを利用できるLinuxのプロジェクトルートで実行する。

```sh
go test ./... -count=1
go vet ./...
go test -race ./src/traversal ./src/repository ./src/ecosystem/... ./src/sourceinspect -count=1
go test ./src/repository -run '^$' \
  -bench 'BenchmarkRepositoryExploration/files_.*/(shared_full_profile|legacy_full_profile)$' \
  -benchmem -benchtime=500ms -count=3
```

上記の全テスト、静的検査、競合検出付きテスト、性能計測は今回の環境で成功した。競合検出付きテストの成功は、キャッシュの並行利用が可能であることを意味しない。
